## Context

当前系统使用 `config/portfolio.yaml` 管理股票（targets）和信息源（sources），这是为股市分析场景设计的。但系统的核心（DAG 引擎、节点系统、配置驱动）是领域无关的，应该能够支持任意领域的应用。

**当前状态**：
- `portfolio.yaml` 包含 `targets` 和 `sources` 两个顶层字段
- Target 有 `code`, `name`, `holding`, `sources` 字段
- Source 有 `name`, `type`, `url`, `regex`/`selector` 字段
- 节点通过 `source_names` 字段引用信息源
- 数据模型中 `RawItem.stock_codes` 是股市专属字段

**约束**：
- 不考虑向后兼容，当前没有外部用户
- 迁移可以通过一次性脚本完成
- Handler 是动态加载的，不需要重新编译程序

## Goals / Non-Goals

**Goals:**
- 将领域特定概念（Portfolio, Target, Source）重构为通用的 Entity 系统
- 支持任意领域的应用（股市、天气、新闻等）通过配置实现
- 提供字段级权限控制，支持节点实例提权
- 保持配置文件 + Web UI 双模式支持
- 实体引用支持 UUID 和业务 ID 双模式

**Non-Goals:**
- 不修改数据库中的领域特定表（`Advice`, `EventRecord` 等可以保留）
- 不提供向后兼容的迁移路径（一次性迁移即可）
- 不实现完整的 RBAC 系统（只做字段级权限）
- 不实现实体版本控制或审计日志

## Decisions

### 决策 1：Source 作为 Entity 的一种类型

**选择**：Source 不再是独立概念，而是 Entity 的一种类型（`rss-source`, `web-source`）

**理由**：
- Source 和 Target 本质上都是"系统关心的对象"，只是用途不同
- 统一存储简化了系统架构（一套 CRUD API，一套权限系统）
- 便于扩展（未来可以添加 `api-source`, `database-source` 等）

**替代方案**：
- 保留 `sources.yaml` 独立文件：增加维护成本，两套系统
- Source 作为 Target 的属性：限制了 Source 的复用性

### 决策 2：实体标识使用 UUID + 业务 ID 双模式

**选择**：实体使用 UUID 作为唯一标识，同时支持业务 ID 引用（`stock:00700.HK`）

**理由**：
- UUID 保证全局唯一性，避免不同类型实体的 ID 冲突
- 业务 ID 提供可读性，便于手写配置和日志查看
- 双模式兼顾了系统需求和用户体验

**替代方案**：
- 只用 UUID：不可读，用户体验差
- 只用业务 ID：需要保证跨类型唯一性，复杂度高

### 决策 3：字段权限采用黑名单机制

**选择**：默认所有字段可读写，只在 entity_types 里声明需要限制的字段

**理由**：
- 大部分字段不需要权限控制，白名单会导致配置冗余
- 黑名单机制更符合"默认开放"的设计理念
- 节点实例可以提权（从 `read-only` 到 `read-write`），但不能降权

**替代方案**：
- 白名单机制：每个字段都要声明权限，配置繁琐
- 无权限控制：无法保护敏感字段（如 `internal_notes`, `api_key`）

### 决策 4：实体关系采用无方向设计

**选择**：`entity-relations.yaml` 使用 `entities: [...]` 列表，不区分 from/to

**理由**：
- 简化查询逻辑（不需要反向查找）
- 关系的语义由 `type` 字段表达（`uses-source`, `depends-on` 等）
- 大部分关系是对称的（A 使用 B ⇔ B 服务 A）

**替代方案**：
- 有方向关系：需要维护双向索引，复杂度高
- 图数据库：过度设计，当前规模不需要

### 决策 5：节点配置优先于关系定义

**选择**：当节点配置和 `entity-relations.yaml` 冲突时，节点配置优先

**理由**：
- 节点配置是运行时行为的直接表达，应该有最高优先级
- `entity-relations.yaml` 主要用于自动发现和 UI 可视化，是辅助性的
- 允许用户在特定场景下覆盖默认关系

**替代方案**：
- 关系定义优先：限制了节点的灵活性
- 冲突报错：过于严格，降低了可用性

### 决策 6：实体配置放在节点的 config 里

**选择**：`entities` 和 `entity_permissions` 字段放在节点的 `config` 里，而不是顶层

**理由**：
- 与其他节点参数（`source`, `timeout_seconds` 等）保持一致
- 简化节点模型，避免顶层字段过多
- 便于 Inspector UI 统一处理（都在 SchemaForm 里）

**替代方案**：
- 顶层字段：语义上更清晰，但增加了节点模型的复杂度
- 混合方式：不一致，增加理解成本

## Risks / Trade-offs

### 风险 1：迁移脚本失败导致数据丢失

**缓解措施**：
- 迁移前备份 `config/portfolio.yaml`
- 迁移脚本生成新文件，不删除旧文件
- 提供验证脚本，检查迁移结果的完整性

### 风险 2：UUID 引用降低配置文件可读性

**缓解措施**：
- 优先使用业务 ID 引用（`stock:00700.HK`）
- UUID 只在程序生成的配置中使用
- Inspector UI 显示时使用 `display_template`（如 `Tencent (00700.HK)`）

### 风险 3：权限系统增加节点开发复杂度

**缓解措施**：
- 默认全可读写，大部分节点不需要关心权限
- 提供简单的 API（`context.get_entity()`, `context.save_entity()`）
- 权限检查在框架层完成，节点代码无感知

### 风险 4：实体类型扩展可能导致配置爆炸

**缓解措施**：
- 提供 `generic` 类型，不验证 attributes（适用于简单场景）
- 鼓励复用现有类型（通过 attributes 扩展，而不是创建新类型）
- Web UI 提供模板，降低配置门槛

### Trade-off 1：灵活性 vs 复杂度

**选择**：优先灵活性，接受一定的配置复杂度

**理由**：
- 目标是领域无关平台，必须支持任意场景
- 复杂度可以通过 Web UI 和文档降低
- 配置文件是高级用户的工具，可以接受一定学习成本

### Trade-off 2：性能 vs 可读性

**选择**：业务 ID 引用需要运行时解析，牺牲少量性能换取可读性

**理由**：
- 实体数量不大（几十到几百），解析开销可忽略
- 可以通过缓存优化（首次解析后缓存 UUID）
- 可读性对调试和维护的价值远大于性能损失
