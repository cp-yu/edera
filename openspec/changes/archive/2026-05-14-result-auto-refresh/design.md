## Context

结果浏览能力已经围绕最新 `Briefing` 工作：`/results` 服务端渲染当前摘要、最新简报、失败源和历史简报；`GET /api/briefings/latest` 返回最新 `Briefing`。FR42 只要求新结果到达时 Web 界面自动刷新，不要求实时协作、跨用户推送或后台通知。

现有项目没有复杂前端框架。第一版应保持在结果页模板内使用原生浏览器 API，避免为了 P2 需求引入常驻连接、外部依赖或新的前端构建链。

## Goals / Non-Goals

**Goals:**

- 结果浏览页能够周期性检查最新 `Briefing` 版本。
- 检测到 `Briefing.id` 或 `created_at` 变化时，当前结果页自动重新加载并保留当前 URL 查询参数。
- 无 `Briefing` 时保持空状态，不进入错误循环。
- 实现面限制在 Web 结果浏览能力内。

**Non-Goals:**

- 不引入 WebSocket、SSE、Redis、消息队列或前端框架。
- 不改变管道产出流程、数据库模型或 `Briefing` 写入语义。
- 不自动刷新简报详情页或建议详情页，除非后续需求明确要求 deep link 实时更新。
- 不实现浏览器通知、声音提醒或多标签页协调。

## Decisions

1. 使用轮询版本检查而不是 WebSocket/SSE。

   依据：现有 `/api/briefings/latest` 已能表达最新结果；FR42 的核心是“新结果到达后页面更新”，不是毫秒级推送。轮询用少量模板脚本即可完成，部署和测试面最小。WebSocket/SSE 需要连接生命周期、断线重连、服务端事件广播和测试设施；在当前 P2 需求下复杂度不值。

2. 以 `Briefing.id` 和 `created_at` 作为结果版本。

   依据：`Briefing.id` 标识数据库记录，`created_at` 标识生成时间；两者都已存在于模型和 API。客户端保存初始版本，后续比较最新 API 响应即可判断是否出现新结果。无记录时版本为空，轮询继续等待第一条 `Briefing`。

3. 在 `/results` 页面挂载自动刷新逻辑。

   依据：FR42 指向 Web 界面查看新结果，当前结果页是最新简报与当前摘要的聚合入口。页面刷新可复用服务端渲染逻辑、保留筛选 URL，不需要重复实现局部 DOM 更新。

4. 使用保守轮询间隔。

   依据：结果生成周期通常远慢于页面交互。默认可使用约 15 秒间隔，既能满足“自动刷新”，也避免本机 API 被高频请求打扰。实现时应让间隔作为模板中的常量或 `data-*` 值，避免散落魔法值。

## Risks / Trade-offs

- [Risk] 用户正在填写筛选表单时页面刷新可能打断输入 → Mitigation: 只在结果版本变化时刷新；实现可跳过当前聚焦在表单控件时的即时刷新，或接受页面级刷新并在测试中固定当前 URL 参数保留。
- [Risk] API 临时失败导致控制台噪声或循环重试 → Mitigation: 捕获 fetch 错误，下一轮继续检查，不改变页面内容。
- [Risk] 轮询不是严格实时 → Mitigation: FR42 未要求亚秒级推送；轮询间隔是明确可调的第一版折中。
- [Risk] `created_at` 字符串格式变化影响比较 → Mitigation: 优先比较 `id`，`created_at` 作为补充版本字段。
